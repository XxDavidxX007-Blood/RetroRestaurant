# 🗄️ Domicilios — Modelo y Consultas SQL

## ¿Qué es?

`models/Domicilio.php` centraliza las consultas SQL del panel admin. Todas operan sobre la tabla `pedido` — no hay tabla propia para domicilios. El filtro base en todas las queries es el tipo de pedido.

---

## El filtro base — siempre presente

```sql
(tp.nombre_tipo LIKE '%domicilio%' OR tp.nombre_tipo LIKE '%delivery%')
```

Este `WHERE` aparece en **todos** los métodos del modelo. Es lo que convierte una query de pedidos genérica en una query de domicilios.

---

## Métodos del modelo

### KPIs

```sql
-- getDomiciliosHoy():
SELECT COUNT(*) FROM pedido p
JOIN tipo_pedido tp ON p.id_tipo_pedido = tp.id_tipo_pedido
WHERE DATE(p.fecha_pedido) = CURDATE()
  AND (tp.nombre_tipo LIKE '%domicilio%' OR tp.nombre_tipo LIKE '%delivery%')

-- getDomiciliosAyer():
-- Igual pero CURDATE() - INTERVAL 1 DAY

-- getConteoByEstado($nombre_estado):
SELECT COUNT(*) FROM pedido p
JOIN tipo_pedido   tp ON p.id_tipo_pedido   = tp.id_tipo_pedido
JOIN estado_pedido ep ON p.id_estado_pedido = ep.id_estado_pedido
WHERE (tp.nombre_tipo LIKE '%domicilio%' OR tp.nombre_tipo LIKE '%delivery%')
  AND ep.nombre_estado = :estado
-- Sin filtro de fecha → cuenta el total histórico de ese estado
```

---

### `getAll($filtro_estado, $filtro_fecha, $pagina, $por_pagina)`

```sql
SELECT
    p.id_pedido,
    p.fecha_pedido,
    ep.nombre_estado                  AS estado,
    ep.id_estado_pedido,
    COALESCE(u.nombre, 'Sin cliente') AS nombre_cliente,
    COALESCE(u.apellidos, '')         AS apellidos_cliente,
    COALESCE(u.telefono, '—')         AS telefono_cliente,
    IFNULL(f.total_factura, 0)        AS total
FROM pedido p
JOIN tipo_pedido   tp ON p.id_tipo_pedido   = tp.id_tipo_pedido
JOIN estado_pedido ep ON p.id_estado_pedido = ep.id_estado_pedido
LEFT JOIN cliente  c  ON p.id_cliente       = c.id_cliente
LEFT JOIN usuario  u  ON c.id_usuario       = u.id_usuario
LEFT JOIN factura  f  ON f.id_pedido        = p.id_pedido
WHERE (tp.nombre_tipo LIKE '%domicilio%' OR tp.nombre_tipo LIKE '%delivery%')
  [AND ep.nombre_estado = :estado]
  [AND DATE(p.fecha_pedido) = :fecha]
ORDER BY p.id_pedido DESC
LIMIT :limit OFFSET :offset
```

El WHERE se construye dinámicamente igual que en pedidos y reservas.

---

### `crear($datos)`

```php
// Primero busca el id del tipo 'domicilio':
$tp = $db->query("SELECT id_tipo_pedido FROM tipo_pedido WHERE nombre_tipo LIKE '%domicilio%' LIMIT 1")->fetchColumn();
if (!$tp) throw new Exception("No existe tipo de pedido 'domicilio'");

// Luego inserta el pedido:
INSERT INTO pedido (id_cliente, id_mesero, id_tipo_pedido, fecha_pedido, id_estado_pedido)
VALUES (:id_cliente, :id_mesero, :id_tipo_pedido, :fecha_pedido, :id_estado_pedido)
```

No inserta en `detalle_pedido` ni en `factura` — el domicilio se crea vacío desde el panel admin.

---

### `cambiarEstado($id_pedido, $id_estado_pedido)`

```sql
UPDATE pedido SET id_estado_pedido = :e WHERE id_pedido = :id
```

Mismo UPDATE que en el modelo de Pedido — sin validación de transiciones.

---

### `eliminar($id_pedido)`

```php
BEGIN TRANSACTION
  DELETE FROM detalle_pedido WHERE id_pedido = :id  -- primero los detalles
  DELETE FROM factura         WHERE id_pedido = :id  -- luego la factura
  DELETE FROM pedido          WHERE id_pedido = :id  -- finalmente el pedido
COMMIT
```

El orden importa por las foreign keys. Si se borrara `pedido` primero, los DELETE de `detalle_pedido` y `factura` fallarían (o quedarían huérfanos dependiendo de la configuración de FK).

---

### Catálogos

```sql
-- getEstados():
SELECT id_estado_pedido, nombre_estado FROM estado_pedido ORDER BY id_estado_pedido

-- getClientes():
SELECT c.id_cliente, u.nombre, u.apellidos, u.telefono
FROM cliente c JOIN usuario u ON c.id_usuario = u.id_usuario ORDER BY u.nombre

-- getMeseros():
SELECT m.id_mesero, u.nombre, u.apellidos
FROM mesero m JOIN usuario u ON m.id_usuario = u.id_usuario ORDER BY u.nombre
```

---

## Relación entre tablas

```
pedido (tipo=domicilio)
  ├── id_tipo_pedido   → tipo_pedido (nombre_tipo LIKE '%domicilio%')
  ├── id_estado_pedido → estado_pedido
  ├── id_cliente       → cliente → usuario
  ├── id_mesero        → mesero  → usuario
  ├── id_pedido        → detalle_pedido (productos)
  └── id_pedido        → factura (total)
```

---

## Diferencia con el modelo de Pedido

| Aspecto | Pedido.php | Domicilio.php |
|---|---|---|
| Filtra por tipo | No (todos los tipos) | Sí (`LIKE '%domicilio%'`) |
| Tiene `getDetalle()` | Sí | No |
| Tiene `getById()` | Sí | No |
| Eliminar | No tiene | Sí (con transacción) |
| Crear | No tiene (lo hace CompraController) | Sí |

---

## Cosas a tener en cuenta

- **El `LIKE '%domicilio%'`** es flexible — funciona si el tipo se llama "domicilio", "Domicilio", "delivery a domicilio", etc. Pero si el tipo se llama solo "delivery" sin "domicilio", también lo captura por el segundo `OR`.
- **No hay `getDetalle()`** en el modelo — si se quisiera ver los productos de un domicilio desde el panel admin, habría que usar el modelo de Pedido o agregar el método.
- **El modelo no valida que el mesero exista** — si `id_mesero = 0` llega al INSERT, la FK fallará y el modelo retornará el mensaje de error.
